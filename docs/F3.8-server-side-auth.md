## 1. Problem (spoof-hullet)

Tre endpoints stoler i dag på `firebaseUid` som **klienten sender med i request-body**. Klienten kan lyve — enhver med kendskab til en anden brugers Firebase-UID kan opføre sig som den bruger.

| Endpoint | Fil:linje | Hvor UID kommer fra i dag | Konsekvens ved spoof |
|---|---|---|---|
| `POST /api/scan` | `api/scan.ts:44` | `req.body.firebaseUid` | Andres konti krediteres point/kroner/CO₂; ledger-rækker skabes på andres vegne |
| `POST /api/redeem` | `api/redeem.ts:18-19` | `req.body.firebaseUid` | Enhver kan dræne enhver users spendable_points ved at kende UID+rewardId |
| `POST /api/portal-features` | `api/portal-features.ts:38-41` | `req.body.firebaseUid` | Selve RPC'en tjekker admin-rolle server-side, men UID'en der slåes op er stadig klient-styret. Hvis en admins UID lækker, kan enhver ændre feature-flags via den UID |

Sekundært: `server.ts` wire'r i dag kun `/api/scan`, `/api/b2b-advisor`, `/api/chat`. `/api/redeem`, `/api/portal-features` og resten af `api/*.ts` er Vercel-file-routing — de er kun aktive i Vercel-deploy, ikke i lokal `tsx server.ts` / Docker. F3.8 skal derfor både lukke spoof-hullet **og** afklare hvor endpoints kører.

---

## 2. Mål

1. Server verificerer et Firebase ID-token på hver privileged request.
2. `firebaseUid` fjernes fra request-body — den udledes af `decodedToken.uid` server-side.
3. Demo-bypass bevares som **eksplicit markeret test-sti**, kun aktiv når `CIRKEL_AUTH_MODE=demo`.
4. Ingen klient-kode ændres i denne plans scope — kun `api/*.ts` og en ny middleware.

---

## 3. Arkitektur

### 3.1 Lib-valg
- **`firebase-admin`** (officiel Google-pakke, Node.js). Aktuel: `^12.6.0`.
- Alternativer overvejet: `firebase-jwt-verify` (letvægts, kun verifikation) — droppet fordi Cirkel også har brug for `getAuth().getUser()` til fremtidig custom-claim brug (admin-rolle direkte i token).
- **Init-strategi**: service-account JSON i env-var (base64-encoded eller stringified). Ikke commit-baseret nøglefil.

### 3.2 Env-vars (tilføjes til `.env.example`, ingen rigtige værdier)
```
# F3.8 — Firebase Admin SDK (server-side ID-token verifikation)
# Fuld service-account JSON, base64-encoded (Vercel/Coolify friendly)
FIREBASE_ADMIN_CREDENTIALS_B64=""

# Auth-mode: "prod" (kræv token) eller "demo" (skip verifikation, log warning)
# Default: "demo" i lokal dev, "prod" i alle deploys hvor CREDENTIALS_B64 er sat.
CIRKEL_AUTH_MODE="demo"
```

### 3.3 Ny fil: `api/_auth.ts` (middleware/helper)
Ansvar:
- Lazy-init Firebase Admin ved første kald (samme mønster som `_ai.ts`, `_claude.ts`).
- Eksporter `requireFirebaseUser(req): Promise<{ uid: string; email?: string; isDemoBypass: boolean }>`.
- Læs `Authorization: Bearer <idToken>` header.
- Verificér token med `admin.auth().verifyIdToken(token, checkRevoked=true)`.
- I `CIRKEL_AUTH_MODE=demo` OG når header mangler: returnér `{ uid: req.body?.firebaseUid, email: req.body?.email, isDemoBypass: true }` + log tydeligt `[F3.8-demo] BYPASS: uid taken from body — DO NOT USE IN PROD`.
- I `prod` OG header mangler/invalid: `throw AuthError(401)`.

### 3.4 Endpoint-ændringer (minimal diff)

**`api/scan.ts`**
- Linje 44: fjern `firebaseUid` fra destructuring af `req.body`.
- Før body-parse: `const user = await requireFirebaseUser(req); if (!user) return res.status(401)...`
- Erstat alle `firebaseUid` med `user.uid`, `email` med `user.email ?? req.body.email` (email er ikke i JWT for anon).
- `fullName` bliver ved med at komme fra body (ikke sikkerhedskritisk — kun display).

**`api/redeem.ts`**
- Linje 18: `const { rewardId } = req.body || {};`
- Linje 19-21: erstat `firebaseUid`-check med `const user = await requireFirebaseUser(req);` — kaster 401 hvis invalid.
- Linje 25: `redeemReward(sb, user.uid, rewardId)`.

**`api/portal-features.ts`**
- POST-branch (linje 37+): erstat `firebaseUid` fra body med `user.uid` fra token.
- `set_portal_features` kaldes med `p_firebase_uid: user.uid` — RPC'en tjekker fortsat admin-rolle server-side (uændret).
- GET-branch: forbliver åben (som i dag) — features er offentlige.

**Ikke ændret i denne plan** (afventer separat vurdering):
- `/api/leaderboard`, `/api/rewards`, `/api/dashboard`, `/api/sorting-rules`, `/api/chat`, `/api/b2b-advisor` — ingen af dem persisterer på vegne af en bestemt user i dag. Hvis det ændrer sig, samme mønster.

### 3.6 Klient-side (skitse — udføres i src/-session)
Ikke i denne plans scope. Ændring der ér nødvendig:
```ts
// src/lib/api.ts eller lignende
import { getAuth } from 'firebase/auth';
async function apiFetch(path: string, body: unknown) {
  const user = getAuth().currentUser;
  const idToken = user ? await user.getIdToken() : null;
  return fetch(path, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      ...(idToken ? { Authorization: `Bearer ${idToken}` } : {}),
    },
    body: JSON.stringify(body),
  });
}
```

## 4. Demo-bypass strategi

CLAUDE.md siger: `quick-demo-login-bypass`-knappen skal blive ved med at virke. Løsning:
1. `CIRKEL_AUTH_MODE=demo` sat → server accepterer requests uden header.
2. Alle demo-bypass-requests logges med `[F3.8-demo]`-prefix så det er tydeligt i logs.
3. Deploy-hooks (Vercel prod, Docker/Coolify prod) skal sætte `CIRKEL_AUTH_MODE=prod` — sikret via checklist nedenfor.
4. I `prod` afvises requests uden gyldigt token med `401 { error: "auth-required" }`.

### Fail-safe
Hvis `CIRKEL_AUTH_MODE=demo` **og** `FIREBASE_ADMIN_CREDENTIALS_B64` er sat: log fedt-typet warning, men **kør stadig i demo**. Sæt aldrig demo som default i prod-deploy.

## 5. Test-plan

### 5.1 Lokal (`npm run dev`, ingen creds)
- [ ] `POST /api/scan` uden header → success (demo-bypass, uid fra body)
- [ ] Logs viser `[F3.8-demo] BYPASS`
- [ ] Ingen crash i `firebase-admin`-init (lazy)

### 5.2 Preview (Vercel, `CIRKEL_AUTH_MODE=prod`, real creds)
- [ ] `POST /api/scan` uden header → 401
- [ ] `POST /api/scan` med gyldig Bearer-token → success, uid = decoded.uid
- [ ] `POST /api/scan` med forfalsket UID i body → uid i DB bliver decoded.uid (body ignoreres)
- [ ] `POST /api/redeem` med token fra User A og rewardId → ledger-linjen tilhører A
- [ ] `POST /api/redeem` med token fra User A men body `firebaseUid: "<user-b-uid>"` → user A dræner ikke B
- [ ] `POST /api/portal-features` fra ikke-admin token → 403 (RPC afviser)
- [ ] `POST /api/portal-features` uden token → 401 (før RPC kaldes)

- [ ] `GET /api/portal-features` (åben endpoint) svarer stadig uden header
